# Automatic tenant account invitations

Management: `/communications/invitations`, linked from Communications. Owners and administrators (revalidated against current database active status/role) can control invitation automation, run it immediately and reissue eligible failed/expired invitations. Managers and caretakers cannot control account creation.

The existing secret-protected daily cron processes invitations at 08:00 Africa/Nairobi. The rollout migration explicitly enables invitation automation for MMAMBUGUA HOSTEL (`mama-mbugua-hostel`) as requested; other organizations default off. Each organization run prepares up to 30 never-invited candidates and sends up to 30 queued invitations. Remaining candidates are picked up on later daily runs. Only current ACTIVE students with a RESERVED/ACTIVE allocation in the same active organization, room and semester qualify. Existing enabled accounts, stored portal passwords, previous portal logins and explicitly blocked access are excluded. No arbitrary public self-registration or password reset is introduced.

Automatic delivery requires a valid registered student email and the existing RESEND_API_KEY, RECEIPT_EMAIL_FROM and SESSION_SECRET configuration. Missing email records are visible to management and do not block email-ready recipients; up to 1,000 missing-email records with an added email are rechecked per run. WhatsApp automatic delivery remains dependent on a Business sender integration. The invitation email contains a private activation link, not a password. One recipient is used per provider request. Provider acceptance is recorded separately from confirmed mailbox delivery. Definite rate-limit failures have up to three attempts; ambiguous sends require provider review and are not automatically resent. Failed/expired invitations can be reissued by an owner/admin, with a new generation that invalidates the old link. Used invitations and existing accounts cannot be reset this way.

The invitation token is a deterministic HMAC over the random invitation ID, generation, recipient and exact expiry, using the server-only session secret. Only its SHA-256 hash is persisted. The sender can reproduce the same token/payload for a definite retry without storing the bearer credential in plaintext. Expiry is 72 hours after the first send attempt. Sender, recipient and hostel-name snapshot are frozen for a generation. Email changes invalidate pending links. No token/password is written to audit metadata or invitation management UI; the provider necessarily receives the activation link in the email body.

`/tenant/activate/[token]` checks the token hash, unused state, expiry, current tenancy, matching registered email and account eligibility. GET only renders the form: email link scanners cannot consume a link or enable an account. Passwords must match and contain 10–128 characters. Activation checks again inside a transaction after locking student and invitation rows, writes a bcrypt password hash, enables the portal, consumes/clears the token hash and creates an audit record atomically. A repeated POST cannot overwrite the password. The student then signs in using the registered mobile number or email and the chosen password; accommodation acceptance remains a separate explicit action. Activation pages are dynamic, noindex, private/no-store and use no-referrer headers and metadata.

Disabling access now sets `portalInviteBlocked=true`; manually enabling/resetting it clears the flag. The additive migration backfills the flag for disabled accounts with previous login/password or a recorded STUDENT_PORTAL_DISABLED audit. It does not change existing passwords or enabled sessions. `TenantPortalInvitation` has a unique organization/student key and unique token hash. Worker, reissue and activation locks share student-then-invitation ordering. Audit metadata identifies the student/invitation and setting changes, not credentials.

Validation: 8 invitation unit tests plus 47 existing gated tests (55 total), TypeScript, targeted ESLint, Prisma validation and production Next build. An isolated PostgreSQL-compatible database applied all 25 migrations. Actual HTTP/server-action tests verified automatic candidate selection with an injected fake email provider, missing email and blocked-account exclusion, repeat-run safety, scan-safe GET, confirmation mismatch rejection, one-use activation, expired/consumed links, mobile-number login and owner/caretaker access. Expiry fixtures use application-clock timestamps consistently. No real student email was sent or real account activated during verification. Native PostgreSQL concurrency, browser hydration and actual mailbox delivery are not established by these tests.
