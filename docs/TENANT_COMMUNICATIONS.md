# Tenant communication centre

Management: `/communications`. Tenant inbox: `/tenant/messages` (linked from account).

Active OWNER, ADMIN and MANAGER database roles may publish. The server resolves audiences to ACTIVE students with a RESERVED or ACTIVE allocation, and checks student, room, semester and allocation organization scope. Guardians, former tenants and public visitors are excluded. Portal read and read-state updates require enabled tenant account and current tenancy; a student cannot read another recipient's messages. Authenticated pages are dynamic and tenant inbox is noindex.

Announcements support all or selected current tenants, general/payment/holiday/examination categories, editable templates and optional scheduling in Africa/Nairobi time (within one year). Scheduled inbox messages become visible on the first visit after their publish time. Each recipient has a private record. Rendering uses escaped React text, not HTML. Read receipts are explicit Mark as read acknowledgments, not proof a message was fully read. The management history shows the latest 100 recipient records. Request UUID plus per-student unique index makes repeated publication idempotent. Publication and audit writes are atomic. Up to 5,000 recipients per announcement; larger audiences reject without partial publication.

Automations default off and can be enabled by management. The prior daily payment queue builder is replaced by these opt-in, current-tenant rules. A missing CRON_SECRET was configured for the production job as part of rollout. The existing secret-protected daily `/api/cron/payment-reminders` route runs communication processing at the existing 05:00 UTC / 08:00 Nairobi schedule:
- Balance messages on the 7th and 10th: recorded unpaid/partial/overdue charges due within three days, minus unreversed payments. One record per charge, student and Nairobi date. No new charges or changes to semester billing.
- Holiday arrangements: one reminder per upcoming BreakPeriod per current tenant, within seven days of start. It asks management to confirm intent/retention/charges, and does not declare intent or assess charges automatically. Upcoming holiday records must exist; this feature does not create a holiday calendar.
- Examination wishes: management provides the dates by scheduling an announcement; exam dates are not inferred.

Optional WhatsApp copies enter the existing manual notification queue during daily processing. They are never labelled delivered automatically. The queue rechecks tenancy and organization WhatsApp settings and locks the message while creating its notification reference. A maximum of 500 pending copies is handled per run, with remaining copies carried forward. No WhatsApp Business provider is connected in this change. Management uses Reminders to open each composer, send, then mark sent. Automated external WhatsApp delivery requires a separate provider integration. Queued messages include the tenant login link and no password or bypass token.

Student login now accepts registered mobile number or email with the existing portal password. Kenyan local and international phone forms use the same normalization as the database identifier index. Ambiguous enabled accounts across organizations are rejected rather than choosing an account. Portal enable/reset no longer requires email when a mobile number exists. No password reset link, OTP or passwordless access is introduced.

Additive migration `20261007230000_tenant_communications` creates only CommunicationSettings and TenantMessage. No acceptance, rent, payment or holiday-charge records are changed. Settings changes and publication are audited. No real announcements are preseeded; no real tenants are messaged by deployment.

Validation: 11 communication unit tests plus 26 existing terms tests; TypeScript, targeted ESLint, Prisma schema validation and production Next build. An isolated PostgreSQL-compatible PGlite database applied all 23 migrations and exercised actual HTTP Server Actions for mobile login, selected/all audiences, cross-student isolation, foreign recipients, caretaker rejection, duplicate posts, scheduled visibility and read acknowledgments. Actual reminder processing generated three balance/holiday records and three WhatsApp queue entries; repeat run generated none. The database/recipients were fictional and isolated. This is not a native PostgreSQL concurrency test, browser hydration test or proof of external WhatsApp delivery.

## Private tenant-to-management conversations and email copies

`/tenant/contact` is available from tenant account and messages pages. Current ACTIVE tenants with enabled portal access and a current RESERVED/ACTIVE allocation may create private questions, maintenance requests, payment questions, complaints or other requests. Tenant identity comes from the authenticated session. Students can follow up; only active OWNER/ADMIN/MANAGER users of the same organization may read and reply through `/communications/inbox`. Caretakers, guardians, anonymous users and other students cannot access a conversation. Management retains historical conversations; replies require the tenant still be eligible.

Conversation lists have pagination (30 per tenant page, 50 per management page). Threads show the latest 50 messages, with older entries retained in the database. Status OPEN indicates awaiting management; a management reply changes it to REPLIED and adds a private inbox notification. This is an asynchronous inbox, not an emergency hotline or live chat. The tenant page directs emergencies to the hostel contact. Per-request UUID uniqueness, transactional writes and bounded messages guard duplicate submissions. New student requests serialize on the student row; replies serialize on the scoped conversation. Sending is limited to five new requests per minute and five replies per conversation per minute. Audit logs store actor/record identifiers and request type, not private message bodies.

Email is optional per announcement and in reminder settings; all options default off. It uses the existing server-only RESEND_API_KEY and RECEIPT_EMAIL_FROM, one registered tenant email per request, and the daily authenticated cron. At most 30 email records are processed per run; remaining queued records carry forward. Missing/invalid emails and former tenants are recorded as MISSING_EMAIL or INELIGIBLE without calling a provider. Sender and recipient are frozen when claimed, and message bodies are immutable. Each generation has a stable provider idempotency key. Provider acceptance is recorded as PROVIDER_ACCEPTED with a provider ID, not delivery to the mailbox. Delivery/bounce webhook tracking is not introduced here.

Definite rate-limit rejections retry on a later daily run, up to three attempts. Permanent errors and missing addresses have a management Retry email button after correcting the details; that creates a new send generation. Timeouts, ambiguous responses or server errors go to REVIEW, without automatic retry that could resend after the provider's 24-hour idempotency window. A worker interrupted after claiming can leave SENDING; management must reconcile that state with the provider before resending. Settings changes and manual retries are audited. Private reply email notifications contain only an invitation to open the authenticated conversation, not the sensitive reply body. Incoming email replies do not become conversations; students reply in the portal.

Migration `20261007233000_tenant_conversations_email` adds conversation/entry tables and default-off email fields to the existing communication tables. No existing account, rent or acceptance records change. Validation adds 10 contact/email unit tests (47 total gated tests), TypeScript, targeted ESLint, Prisma validation and production Next build. Isolated HTTP integration applies all 24 migrations and verifies actual two-way Server Actions, private inbox scoping, foreign/caretaker/student denial, repeat submission safety and an actual email outbox with an injected fake provider. No real student contacted and no external email sent during verification. Native PostgreSQL concurrency, browser hydration and actual mailbox delivery remain unverified by these tests.
