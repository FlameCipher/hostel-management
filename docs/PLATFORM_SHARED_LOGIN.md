# SYSTEM IN ONE shared login

StudentsHostels remains at https://studentshostels.com. SYSTEM IN ONE manages the verified organization membership and product entitlement. Existing hostel credentials and records remain in the hostel database.

The hostel starts authorization with a random state cookie and verifier cookie, both HTTP-only, secure in production, SameSite=Lax and limited to ten minutes. The platform authorization page requires its existing customer session, verified active user, current session version, active organization, and active StudentsHostels entitlement within its start/end window. An explicit action issues a five-minute, one-use opaque code through the authenticated backend bridge. The database stores the code hash and S256 challenge only. The fixed callback verifies browser state and the original verifier; all redirects and bridge destinations are fixed HTTPS addresses.

Unlinked accounts require the existing hostel login, explicit account confirmation and a fresh hostel password check. First organization adoption requires owner access in both systems. Later users can link their own existing hostel account within the already-mapped organization. Foreign organization mappings and existing identity conflicts are rejected. Grant consumption, identity mapping and aggregate audits are transactional, with row/advisory locks and a unique organization/user mapping. A maximum of five confirmation attempts persists independently of a rolled-back repair transaction. Local passwords, hostel roles and tenant/financial records are not migrated or overwritten.

Mapped accounts sign in with their existing hostel role. Platform OWNER is required for a local OWNER role; platform OWNER/ADMIN for local ADMIN/MANAGER; any valid platform member for CARETAKER. Platform roles never upgrade the local role. Every shared-session request revalidates platform access and session version, plus current local account, role and organization status. React request caching avoids duplicate checks within one request; there is no cross-request authorization cache. Platform unavailability fails closed for shared sessions. Ordinary hostel password sessions retain their existing behavior.

Set the same dedicated HOSTEL_SSO_SECRET in both production projects. The existing provisioning and HealthFix credentials are separate. This implementation does not change provisioning records or grant commercial access; existing organizations must have active platform membership and entitlement before linking. It does not implement student SSO, cross-site logout propagation, platform provisioning adoption updates, or automated account merges. Existing invitations/receipts and the old working domain alias remain valid.

Validation: unit cryptographic/protocol checks, platform membership/revocation checks, isolated PostgreSQL-compatible mapping/role/expiry/replay/attempt tests and two-application HTTP sign-in tests. Native PostgreSQL concurrency, full browser hydration and the real owner's account confirmation require separate verification. No production users are linked during deployment.
