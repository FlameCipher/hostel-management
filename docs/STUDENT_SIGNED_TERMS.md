# MMAMBUGUA HOSTEL student terms

Scope: existing organization `mama-mbugua-hostel` only. Other landlords and platform organizations do not receive MMAMBUGUA terms. Contact 0714 464 701; Gachororo, Highpoint Road, approximately 500 metres from JKUAT Gate B. Confirmed gate hours: 6:30 a.m. to 10:00 p.m.

After student login, MMAMBUGUA students open `/tenant/terms`; the account page also links there. A current reserved/active allocation and enabled, non-archived portal identity are required to sign. Students read versioned rules, their room, semester dates and recorded semester rent, then explicitly accept accommodation and all displayed terms with the digital acceptance button. This records digital acceptance, not a handwritten or certificate-based signature. Earlier version v1 used a typed signature and checkbox; saved v1 copies retain that method. Rent remains charged by the existing accounting system; acceptance adds no charge or penalty. The existing statement remains accessible.

Signing locks the student and submitted allocation, rechecks current identity/allocation/organization and the rendered document hash, and rejects stale forms. A unique scope/version key prevents duplicate acceptance. Snapshot, authoritative student name, server date, UUID reference, checksum and audit commit in one transaction. Duplicate submissions return the saved record. No update/delete action exists. Student/organization/allocation deletion is restricted while signed records reference them.

The snapshot preserves the exact terms, contact details, student name/institution/admission number, room, semester dates and recorded rent at signing. PDF downloads read the saved snapshot, not current room/name/rent or the latest rules. A canonical parsed structure avoids JSONB key-order checksum changes. The checksum detects changes; it is not a signature certificate or a guarantee against privileged database manipulation. Future terms changes require a new version and new student acceptance; never rewrite a signed snapshot.

Students download immediately after signing and again from their tenant terms page (latest 100 records). Management `/student-terms` shows current signed/pending allocations with pagination and searchable recent records, with PDF download. Management downloads revalidate an active OWNER/ADMIN/MANAGER record in the same organization. Tenant downloads revalidate portal eligibility and scope to the exact student and organization. Links are authenticated; no public bearer/share token is created. PDF responses are private/no-store and use attachment disposition.

Deploy the additive migration `20261007212500_student_terms_acceptance` before exposing the new pages. The build runs the new terms tests before its existing locked Prisma deploy gate. No destructive migration or seed operation. Existing students need their own enabled portal account and room allocation; management must assist those without portal access. This feature does not automatically enable accounts, send bulk messages, or sign on students' behalf.

Validation: unit tests cover signature consent, identity/allocation/version/view-hash errors, locks, duplicates, auditing, recipient isolation, management authorization, JSONB key reordering, PDF integrity and private download headers. Mocks do not prove live database lock concurrency. Render a fictional sample PDF for visual review. Verify authenticated student signing and tenant/management downloads separately after deployment; do not sign for real students as a test.

## Digital accommodation acceptance (version 2026-10-08-v2)

New agreements use an explicit `Accept accommodation and agree to hostel terms` button after the displayed rules. No typed name or separate signature checkbox is required. The named submit button provides `agree=yes`; missing consent is rejected server-side. Student identity comes from the authenticated, revalidated student record, ignoring any client-supplied name. Snapshot `acceptanceMethod=DIGITAL_ACCEPTANCE` is included in the checksum and PDF. Audit action is STUDENT_TERMS_ACCEPTED.

Version v2 is a new acceptance; existing v1 records remain unchanged and retain their typed-signature wording, checksum and download. The optional snapshot field avoids a migration or retrospective rewriting. A current reservation or occupancy alone is not backfilled as acceptance. Merely visiting the page/login does not accept any agreement. Only the explicit accommodation acceptance action records agreement to the displayed version. Future changes still require a new version. PDF labels identify digital acceptance without claiming a handwritten/certificate signature.

Digital acceptance validation: 26 agreement tests pass, including legacy checksum/PDF compatibility. Isolated HTTP tests using a temporary PostgreSQL-compatible database and running Next server exercise actual login/form POST, missing consent, stale view, saved digital acceptance/audit, PDF download, duplicate prevention, student/hostel isolation, management roles and disabled accounts. These checks do not establish browser layout or native PostgreSQL concurrency; no real student agreement is created.
